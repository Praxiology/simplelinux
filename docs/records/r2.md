# 一、先建立总模型

以大语言模型推理为例，框架管理的并不只是“模型权重”，而是同时管理几类规模巨大的数据：

```text
模型权重 Weight
  ├── 多层 Transformer 参数
  ├── 通常常驻 GPU 显存
  └── 多卡时按 Tensor Parallel / Pipeline Parallel 切分

KV Cache
  ├── 每个请求、每一层、每个历史 token 的 K/V
  ├── 随生成长度动态增长
  └── 通常是推理阶段最大的动态显存对象

激活值 Activation
  ├── 当前 batch 的 hidden states
  ├── Q/K/V、中间 GEMM 结果
  └── 尽量复用、融合或分块

调度元数据 Metadata
  ├── 请求长度
  ├── KV Cache 页表
  ├── batch 中每个请求的 token 位置
  └── CUDA Kernel 的 launch 参数
```

因此，SGLang、vLLM、TensorRT-LLM 的核心问题可以概括为：

```text
如何让大量请求共享 GPU 计算资源，
如何让 KV Cache 尽可能装进显存，
如何避免频繁分配、复制、同步和 Kernel 启动，
如何让 Tensor Core、显存带宽、PCIe/NVLink 同时保持繁忙。
```

从操作系统角度看，它们很像一个专门为 Transformer 设计的“用户态 GPU 内核”。

# 二、一次请求的完整执行链路

假设用户提交：

```text
Prompt = "请解释操作系统中的 DMA"
```

推理过程大致如下：

```text
客户端请求
  ↓
SGLang API Server
  ↓
Tokenizer
  ↓
Scheduler
  ↓
选择 Prefill 或 Decode 阶段
  ↓
准备 GPU Tensor 和 KV Cache 页表
  ↓
提交 CUDA Kernel / CUDA Graph
  ↓
GPU SM、Tensor Core、显存控制器执行
  ↓
采样下一个 token
  ↓
更新 KV Cache
  ↓
再次进入 Scheduler
```

GPU 真实执行链路可以进一步拆开：

```text
CPU 调度线程
  ↓
写入 GPU 可见的 Tensor / Metadata Buffer
  ↓
CUDA Runtime 调用 Driver
  ↓
Driver 写 GPU Command Queue / Doorbell
  ↓
GPU Command Processor 读取命令
  ↓
调度 Copy Engine 或 Compute Engine
  ↓
SM 加载显存数据
  ↓
L2 Cache → Shared Memory → Register
  ↓
Tensor Core / CUDA Core 计算
  ↓
写回 KV Cache、Activation 或输出 Buffer
```

这和工程中的 e1000 驱动非常相似：

```text
CPU 填写网卡描述符
  ↓
MMIO 写发送队列尾指针
  ↓
网卡 DMA 读取描述符
  ↓
设备执行任务
  ↓
设备更新完成状态
```

GPU 只是把这个模型扩展成了大量并行队列、数万个线程和多级缓存。

# 三、模型权重是如何进入 GPU 的

## 1. 启动阶段加载权重

模型文件通常位于：

```text
NVMe / 分布式文件系统 / 对象存储
```

启动时经过：

```text
磁盘
  ↓
Linux Page Cache 或用户态文件读取
  ↓
CPU 内存
  ↓
Pinned Host Memory
  ↓
PCIe DMA / NVLink
  ↓
GPU 显存
```

如果使用多张 GPU，权重通常不会完整复制到每张卡，而是按照并行策略切分。

例如 Tensor Parallel：

```text
完整权重 W
  ↓
W0 → GPU 0
W1 → GPU 1
W2 → GPU 2
W3 → GPU 3
```

每张 GPU 只保存自己负责的矩阵分片。

## 2. CPU 不是逐元素搬运

真正的搬运通常由 GPU Copy Engine 或 CUDA Driver 发起 DMA：

```text
CPU：
  准备源地址、目标地址、长度和传输命令

GPU Copy Engine：
  从 Host RAM 批量读取
  写入 VRAM

CPU：
  等待 CUDA Event 或查询完成状态
```

如果源内存是普通 pageable memory，驱动可能需要先复制到锁页内存：

```text
Pageable RAM
  → Pinned Staging Buffer
  → GPU DMA
  → VRAM
```

高性能框架会尽量使用：

```text
Pinned Memory + cudaMemcpyAsync()
```

从而让数据传输和 GPU 计算重叠。

# 四、SGLang 真正重点管理的对象：KV Cache

对于 Transformer 解码来说，权重通常是静态的，而 KV Cache 是动态增长的。

## 1. 为什么需要 KV Cache

生成第一个 token 时，模型需要处理完整 Prompt：

```text
Prompt:
t0 t1 t2 t3 ... tN
```

每一层 Attention 会产生：

```text
K0, K1, K2, ..., KN
V0, V1, V2, ..., VN
```

如果每生成一个新 token 都重新计算整个 Prompt，计算量会非常大。

因此框架把历史 token 的 K/V 保存起来：

```text
KV Cache:
Layer 0:
  K0, V0, K1, V1, ...

Layer 1:
  K0, V0, K1, V1, ...

Layer N:
  K0, V0, K1, V1, ...
```

下一次只计算新 token 的 Q/K/V，然后让 Q 读取历史 KV。

## 2. KV Cache 为什么不能使用普通连续数组

假设为每个请求分配最大上下文长度：

```text
Request A: 128K token
Request B: 128K token
Request C: 128K token
```

实际请求可能只有：

```text
A: 100 token
B: 2K token
C: 8K token
```

连续分配会浪费大量显存，而且请求结束后容易产生碎片。

因此主流框架普遍采用分页思想：

```text
显存 KV Pool:

Page 0
Page 1
Page 2
Page 3
Page 4
...
```

每个请求通过页表映射到若干物理 KV Page：

```text
Request A:
逻辑 token 0   → Page 17
逻辑 token 128 → Page 4
逻辑 token 256 → Page 91

Request B:
逻辑 token 0   → Page 8
逻辑 token 128 → Page 31
```

这与操作系统的虚拟内存非常接近：

```text
请求逻辑 KV 地址
  ↓
KV Page Table
  ↓
GPU 显存中的物理 Page
```

SGLang、vLLM 和 TensorRT-LLM 都在不同程度上使用这种分页 KV Cache。

# 五、SGLang 的 RadixAttention：把 KV Cache 变成前缀树

SGLang 的代表性机制是 RadixAttention。

它解决的是另一个问题：

```text
不同请求可能拥有相同的 Prompt 前缀。
```

例如：

```text
请求 A:
系统提示词 + 用户问题 A

请求 B:
系统提示词 + 用户问题 B

请求 C:
系统提示词 + 用户问题 C
```

公共前缀：

```text
系统提示词
```

如果每个请求都重复计算并保存这部分 KV，会浪费 GPU 算力和显存。

## 1. Radix Tree 结构

SGLang 可以把 token 前缀组织成 Radix Tree：

```text
Root
 └── [系统提示词]
      ├── [用户问题 A]
      ├── [用户问题 B]
      └── [用户问题 C]
```

树节点对应已经计算好的 KV Cache 页面：

```text
Radix Node
  ├── token prefix
  ├── KV Cache Page 列表
  ├── 引用计数
  ├── 最近使用时间
  └── 是否仍被请求占用
```

当新请求到达时：

```text
1. Tokenize 请求
2. 在 Radix Tree 中查找最长公共前缀
3. 找到可复用的 KV Cache
4. 只对未命中的后缀执行 Prefill
5. 将新后缀追加到 Cache
```

数据流变为：

```text
完整 Prompt
  ↓
Radix Tree 查找
  ↓
命中公共前缀 KV
  ↓
只计算未命中部分
  ↓
追加新 KV Page
```

这不是 GPU 硬件直接提供的功能，而是 SGLang 在 GPU 显存之上实现的缓存管理算法。

GPU 提供的是：

```text
高速显存
异步 Kernel
高效 Attention Kernel
设备端页表/索引读取能力
```

SGLang 负责：

```text
前缀查找
引用计数
页面分配
页面回收
缓存淘汰
请求与页面的映射
```

## 2. RadixAttention 与操作系统的类比

可以这样理解：

| 操作系统 | SGLang |
|---|---|
| 虚拟地址 | 请求逻辑 token 位置 |
| 页表 | KV Page Table |
| 物理页 | GPU KV Cache Page |
| 文件 Page Cache | Prefix KV Cache |
| Copy-on-Write | 共享前缀后分叉 |
| LRU 回收 | KV Cache eviction |
| 缺页异常 | Cache miss / 页面迁移 |
| 内存分配器 | KV Block Manager |

因此 SGLang 的 RadixAttention 更像：

```text
前缀树 + GPU 页缓存 + Attention 地址翻译
```

# 六、Prefill 和 Decode 是两种完全不同的 GPU 工作负载

## 1. Prefill 阶段

Prefill 是处理输入 Prompt：

```text
输入长度可能是几百、几千甚至几十万 token
```

特点：

```text
Q/K/V token 数量多
矩阵运算密集
更适合 Tensor Core
GPU 并行度高
```

典型链路：

```text
Prompt Token
  ↓
Embedding
  ↓
QKV Projection
  ↓
Prefill Attention
  ↓
写入 KV Cache
  ↓
MLP
  ↓
得到第一个输出 token
```

Prefill 通常更偏计算密集型。

## 2. Decode 阶段

Decode 每次通常只为每个请求生成一个 token：

```text
Request A → 1 token
Request B → 1 token
Request C → 1 token
```

但每个新 token 都需要访问很长的历史 KV：

```text
Q_new
  ×
K_history
  ↓
Attention
  ↓
V_history
```

特点：

```text
Q 很小
KV 很长
显存读取多
Kernel 启动开销明显
容易受显存带宽限制
```

因此 Decode 更偏内存访问密集型。

SGLang 的 Scheduler 会把不同请求组织成动态 batch：

```text
本轮 Batch:
  Prefill 请求：A、B
  Decode 请求：C、D、E
```

然后根据 Attention Backend 分别处理。

这种方式称为：

```text
Continuous Batching / In-flight Batching
```

请求不需要等待整个静态 batch 完成，而是：

```text
请求完成 → 立即退出
新请求到达 → 立即加入后续迭代
```

这提高了 GPU 利用率。

# 七、SGLang 如何把分页 KV 交给 GPU Kernel

GPU Kernel 并不需要把每个请求的 KV 重新拼接成一个连续大数组。

它通常接收：

```text
Q Tensor
KV Cache Pool
Page Table
Sequence Length
Query Indptr
KV Indptr
```

简化后的数据结构如下：

```text
kv_cache:
  [物理 page 数量, page_size, kv_heads, head_dim]

page_table:
  Request 0 → [17, 4, 91]
  Request 1 → [8, 31]
  Request 2 → [2, 77, 13, 40]

seq_lens:
  [300, 190, 512]
```

Attention Kernel 内部逻辑类似：

```text
for each request:
    for each logical token:
        page_id = page_table[request][logical_token / page_size]
        offset  = logical_token % page_size
        read kv_cache[page_id][offset]
```

但实际 CUDA Kernel 会做大量优化：

```text
Warp 级加载
向量化访问
L2 Cache 复用
Shared Memory 分块
Tensor Core 计算
Split-KV 并行
在线 Softmax
```

关键是：

```text
框架负责“逻辑地址到物理 Page 的映射”
GPU Kernel 负责“按照映射高效读取并计算”
```

SGLang 中常见的 FlashInfer Backend 就承担了这类高性能 paged attention 执行。

# 八、FlashInfer、FlashAttention 与 GPU 底层元能力

SGLang 并不手写所有底层 GPU 细节，而是使用 FlashInfer、FlashAttention、Triton 或自定义 CUDA Kernel。

它们主要利用以下 GPU 能力。

## 1. 显存层级

数据访问大致经过：

```text
HBM/GDDR
  ↓
L2 Cache
  ↓
Shared Memory
  ↓
Register
  ↓
Tensor Core / CUDA Core
```

高效 Attention Kernel 会把一部分 Q/K/V 分块加载到 Shared Memory：

```text
显存中的 KV Page
  ↓
Coalesced Global Load
  ↓
Shared Memory Tile
  ↓
Warp 计算
  ↓
Register 累积结果
```

尽量避免：

```text
每一次乘加都重新从显存读取数据
```

## 2. Online Softmax

Attention 需要计算：

$$
\operatorname{softmax}(QK^T)V
$$

如果先完整保存 $QK^T$，会产生巨大中间矩阵。

FlashAttention 类 Kernel 会使用分块和在线 Softmax：

```text
读取一块 K/V
  ↓
计算局部 QK
  ↓
更新局部 max 和 sum
  ↓
继续读取下一块
  ↓
直接累积输出
```

这样减少：

```text
显存写入
显存读取
中间矩阵分配
```

## 3. Warp 和线程束协作

GPU 不是逐线程独立完成完整 Attention，而是让一个 Warp 协同处理：

```text
Warp
 ├── 线程 0 加载部分 K
 ├── 线程 1 加载部分 K
 ├── 线程 2 加载部分 V
 └── ...
```

通过：

- Warp shuffle；
- 向量化 load/store；
- Shared Memory；
- Cooperative Groups；

在较少同步的情况下完成归约、Softmax 和矩阵乘法。

## 4. Tensor Core

Prefill 中的线性层主要是 GEMM：

```text
Y = XW
```

GPU 会将矩阵切成 tile，交给 Tensor Core：

```text
Global Memory
  → Shared Memory
  → Tensor Core MMA
  → Register Accumulator
  → Global Memory
```

常见数据类型包括：

```text
FP16
BF16
TF32
FP8
INT8
FP4
```

推理框架会根据 GPU 架构选择对应 Kernel。

# 九、CUDA Graph：减少“提交命令”的 CPU 开销

Decode 阶段有一个特殊问题：

```text
每生成一个 token，就要重复执行很多相同结构的 Kernel。
```

如果每次都由 Python/PyTorch 逐个发起：

```text
Kernel 1
Kernel 2
Kernel 3
Kernel 4
...
```

CPU 端的调度和 CUDA API 开销可能变得明显。

因此 SGLang、vLLM、TensorRT-LLM 都会在条件允许时使用 CUDA Graph：

```text
预热阶段：
  捕获一组 Kernel 调用和依赖关系

执行阶段：
  更新少量输入 Buffer
  直接 replay 整张 GPU Graph
```

数据流变为：

```text
CPU 更新固定地址的 Metadata
  ↓
GPU Replay CUDA Graph
  ↓
批量执行整个 Decode pipeline
```

CUDA Graph 的限制是：

```text
内存地址最好稳定
Tensor shape 需要固定或按 bucket 分类
不能频繁动态分配
控制流不能任意变化
```

所以框架会预先创建多组 Graph：

```text
Batch Size = 1
Batch Size = 2
Batch Size = 4
Batch Size = 8
...
```

实际请求根据规模选择最接近的 Graph，并用 padding 填补空位。

这就像操作系统预先建立一套固定的快速系统调用路径，只在共享内存中修改少量参数。

# 十、SGLang 的 Metadata 为什么非常重要

GPU 计算数据本身可能很大，但很多性能问题来自 Metadata：

```text
每个请求当前长度
每个请求的 KV Page 数量
每个 Page 的物理编号
每个请求的 query 起始位置
每层的 Cache 偏移
Attention mask
Speculative decoding 的验证位置
```

SGLang 会准备类似：

```text
seq_lens
req_pool_indices
kv_indptr
kv_indices
kv_last_page_len
qo_indptr
out_cache_loc
```

它们本质上是 GPU Kernel 的“控制平面输入”。

可以分成两类：

```text
数据面：
  Q、K、V、权重、KV Cache

控制面：
  Page Table、长度、偏移、索引、mask、batch metadata
```

每轮推理通常是：

```text
CPU Scheduler 计算新 Metadata
  ↓
Pinned Host Buffer
  ↓
异步 H2D Copy
  ↓
GPU Attention Kernel 使用
```

高性能框架会努力做到：

```text
避免每轮重新分配 Tensor
避免 Python 对象大量创建
避免同步读取 GPU 状态
避免不必要的 Host ↔ Device 往返
```

# 十一、量化也是一种“大规模数据管理”

量化不仅减少计算精度，也直接减少显存和带宽压力。

例如：

```text
FP16 权重：2 bytes / element
FP8 权重：1 byte / element
INT4 权重：0.5 byte / element
```

对于 KV Cache，量化影响尤其明显：

```text
FP16 KV Cache
  → FP8 KV Cache
  → 更少显存占用
  → 更少 HBM 读取
  → Decode 吞吐提高
```

但 GPU Kernel 需要在读取时进行反量化：

```text
FP8/FP4 KV
  ↓
Scale
  ↓
转换为计算格式
  ↓
Tensor Core / CUDA Core
```

理想实现会把：

```text
读取
反量化
矩阵运算
```

融合在同一个 Kernel 中，避免产生额外中间 Buffer。

因此，量化并不是简单的“把数据变小”，而是：

```text
改变 Cache Layout
改变内存带宽需求
改变 Tensor Core 输入格式
改变 Kernel 调度策略
```

# 十二、MLA 为什么能进一步减少 KV Cache

DeepSeek 类模型使用 Multi-head Latent Attention，核心思想是：

```text
不要为每个 Attention Head 完整保存 K/V，
而是保存压缩后的 latent KV。
```

普通 MHA 的 KV Cache 近似是：

```text
[层数, token 数, KV heads, head_dim]
```

MLA 更接近：

```text
[层数, token 数, latent_dim]
```

因此：

```text
KV Cache 体积下降
显存读取下降
Decode 带宽压力下降
```

但读取时需要额外计算：

```text
压缩 KV
  → 矩阵吸收 / 低秩恢复
  → Attention
```

这是一种典型的数据移动与计算折中：

```text
少存储、少搬运、多一点计算
```

SGLang、vLLM、TensorRT-LLM 都在针对 MLA 开发专门的分页布局和 Attention Kernel。

# 十三、连续批处理如何利用 GPU 的并行能力

假设有三个请求：

```text
A：正在 Prefill，输入 2000 token
B：正在 Decode，生成第 20 个 token
C：正在 Decode，生成第 7 个 token
```

静态批处理可能要求：

```text
等 A、B、C 统一完成
```

连续批处理则把它们合并到一个动态执行批次：

```text
当前轮：
  A 使用 Prefill Kernel
  B 使用 Decode Kernel
  C 使用 Decode Kernel
```

框架需要维护：

```text
每个请求的状态
每个请求的 token 数
每个请求的 KV Page
每个请求在 batch Tensor 中的位置
每个请求的输出位置
```

GPU Kernel 看到的通常是压紧后的 Tensor：

```text
Q = [A 的多个 token, B 的 1 token, C 的 1 token]
```

配合：

```text
cu_seqlens
query_start_loc
seq_lens
block_table
```

Kernel 就能知道每一段属于哪个请求。

这类似于操作系统把多个进程的内存分散存放，再通过页表和元数据让硬件正确访问。

# 十四、多 GPU 推理中的底层数据流

## 1. Tensor Parallel

一个矩阵被切到多张 GPU：

```text
输入 X
  ↓
GPU 0 计算 W0
GPU 1 计算 W1
GPU 2 计算 W2
GPU 3 计算 W3
  ↓
All-Reduce / All-Gather
  ↓
合并结果
```

通信路径可能是：

```text
GPU 0
  ↔ NVLink / NVSwitch
  ↔ GPU 1/2/3
```

或者：

```text
GPU
  ↔ PCIe
  ↔ CPU Root Complex
  ↔ 其他 GPU
```

NCCL 会利用：

- NVLink；
- NVSwitch；
- PCIe P2P；
- RDMA；
- GPUDirect RDMA；

构建通信拓扑。

## 2. Pipeline Parallel

不同 GPU 保存不同 Transformer 层：

```text
GPU 0：Layer 0-15
GPU 1：Layer 16-31
GPU 2：Layer 32-47
GPU 3：Layer 48-63
```

激活值在 GPU 之间流动：

```text
GPU 0
  → Activation
  → GPU 1
  → Activation
  → GPU 2
  → GPU 3
```

重点是让通信和计算重叠：

```text
GPU 0 计算 microbatch 2
GPU 1 同时计算 microbatch 1
GPU 2 同时计算 microbatch 0
```

## 3. Expert Parallel

MoE 模型中，Token 根据 Router 被发送到不同专家：

```text
Token
  ↓
Router
  ├── Expert 0
  ├── Expert 1
  ├── Expert 2
  └── Expert 3
```

跨 GPU 时需要 All-to-All：

```text
GPU 0 的 Token
  → 网络/互连
  → GPU 2 的 Expert
```

这时瓶颈可能不是 Tensor Core，而是：

```text
All-to-All 通信
显存读写
Token 重排
负载不均衡
```

# 十五、Prefill/Decode 分离与 KV Cache 传输

在大型部署中，Prefill 和 Decode 的硬件需求不同：

```text
Prefill：
  计算密集，适合大 batch 和高 Tensor Core 利用率

Decode：
  内存带宽密集，适合较小延迟和大量并发请求
```

因此可以把两者部署到不同 GPU 池：

```text
Prefill GPU 集群
  ↓
生成 KV Cache
  ↓
GPU Direct / RDMA / NVLink
  ↓
Decode GPU 集群
```

数据流：

```text
请求
  ↓
Prefill Worker
  ↓
计算 Prompt 的 KV
  ↓
KV Cache Transfer
  ↓
Decode Worker
  ↓
逐 token 生成
```

这就类似分布式存储中的：

```text
计算节点生成数据
  ↓
高速网络 DMA
  ↓
另一组节点消费数据
```

但需要注意，KV Cache 传输可能非常昂贵，因此框架通常会：

- 分块传输；
- 传输与计算重叠；
- 使用 RDMA；
- 使用 GPU Direct；
- 复用已有前缀；
- 只传输增量 KV；
- 压缩或量化 KV。

# 十六、SGLang、vLLM、TensorRT-LLM 的侧重点

| 框架 | 主要特点 |
|---|---|
| SGLang | RadixAttention、前缀复用、结构化生成、动态调度、FlashInfer |
| vLLM | PagedAttention、KV Block 管理、连续批处理、广泛模型兼容 |
| TensorRT-LLM | NVIDIA GPU 深度优化、融合 Kernel、量化、CUDA Graph、in-flight batching |
| llama.cpp | CPU/GPU 混合、量化、边缘设备和本地推理、CUDA/Metal/Vulkan 后端 |
| DeepSpeed-Inference | 大模型并行、权重分片、Kernel Fusion、分布式推理 |

它们的共同底层思想是：

```text
把 GPU 当成一个高吞吐异步设备，
把显存当成多级缓存和对象池，
把 KV Cache 当成分页虚拟内存，
把 Kernel 提交当成设备队列操作，
把调度元数据当成设备执行计划。
```

# 十七、和 SimpleLinux 的对应关系

SimpleLinux 中的 e1000 路径：

```text
CPU 分配 DMA Buffer
  ↓
填写 Descriptor
  ↓
写 MMIO 寄存器
  ↓
网卡 DMA
  ↓
设备更新 Descriptor 状态
```

推理框架中的 GPU 路径：

```text
CPU Scheduler 分配 KV Page
  ↓
填写 GPU Metadata / Page Table
  ↓
提交 CUDA Kernel 或 Replay CUDA Graph
  ↓
GPU SM / Copy Engine DMA
  ↓
读取权重和 KV Cache
  ↓
Tensor Core 计算
  ↓
写回输出和新的 KV Page
```

对应关系：

| SimpleLinux | 推理框架 |
|---|---|
| 物理帧分配器 | GPU 显存/KV Block Allocator |
| DMA Buffer | KV Cache Pool / Activation Buffer |
| Descriptor Ring | CUDA Command Buffer / Kernel 参数 |
| BAR/MMIO | GPU Driver 控制寄存器和 Doorbell |
| 网卡 DMA | GPU Copy Engine / Compute Memory Access |
| RX/TX Ring | Request Queue / KV Page Table |
| 轮询状态位 | CUDA Event / Fence / Completion |
| `volatile` MMIO | CUDA Driver 提交和同步原语 |
| 中断 | GPU Completion Event |
| VMM 页表 | GPU Virtual Address / KV Page 映射 |

当前 SimpleLinux 还没有真正的 GPU 驱动、GPU 页表或 CUDA Runtime，因此它不能直接运行 SGLang；但它已经展示了理解 GPU 框架所需的几个底层模型：

```text
设备寄存器
DMA
物理内存
虚拟地址
描述符队列
异步完成
驱动与硬件状态机
```

# 十八、最核心的结论

主流推理框架并不是简单地调用：

```text
model(input)
```

它们实际上构建了一个复杂的 GPU 数据管理系统：

```text
请求调度器
  ↓
KV Cache 分页分配器
  ↓
Prefix Cache / Radix Tree
  ↓
GPU Metadata Buffer
  ↓
Paged Attention Kernel
  ↓
显存层级与 Tensor Core
  ↓
CUDA Graph / Stream / Event
  ↓
NCCL / NVLink / RDMA
```

其中：

```text
SGLang 的 RadixAttention：
  管理“哪些历史 KV 可以复用”

Paged KV Cache：
  管理“请求逻辑 token 位于哪些显存页”

FlashInfer/FlashAttention：
  管理“如何高效读取分页 KV 并完成 Attention”

CUDA Graph：
  管理“如何减少重复 Kernel 提交开销”

Tensor Core：
  管理“如何高吞吐执行矩阵乘法”

NCCL/NVLink/RDMA：
  管理“多 GPU 之间如何交换权重、激活和 KV”

量化与融合 Kernel：
  管理“如何减少显存容量、带宽和中间数据搬运”
```

用操作系统的一句话类比：

```text
SGLang/vLLM/TensorRT-LLM
≈
面向 Transformer 的 GPU 内存管理器
+ 请求调度器
+ 异步设备驱动
+ 专用高性能文件缓存
+ 分布式进程间通信层
```

而 GPU 本身提供的“元能力”主要是：

```text
高速显存
GPU 虚拟地址
异步 Copy Engine
大量并发线程
Warp 调度
Shared Memory
L2 Cache
Tensor Core
CUDA Stream/Event
CUDA Graph
NVLink/P2P
RDMA/GPUDirect
```

框架的价值，就是把这些分散的硬件能力组合成一个能够持续处理海量 token、请求和 KV 数据的执行系统。
