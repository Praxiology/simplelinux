# SimpleLinux 开发历程（探索与实现史）

本文记录 SimpleLinux 教学内核从"一句话目标"到"Phase 8 全部落地"的**探索过程**：每一阶段想验证什么、实际怎么做、踩了什么坑、如何做取舍。它与 [`操作手册.md`](操作手册.md)（面向使用/测试）互补——手册讲"如何用",本文讲"如何一步步做出来、为什么这样做"。

> 目标原文（`target.md`）：实现一个简易版的类 Linux 操作系统，涵盖 **内存、进程、线程、虚拟文件系统、驱动、内核态、用户态、网络栈** 几大核心功能，帮助理解与掌握操作系统的核心实现思路。

---

## 1. 总体路线

整个工程按"自底向上、每层可独立观测"的原则拆成串行推进的阶段：

```
P0  工具链与环境           Rust nightly + no_std + x86_64-unknown-none
P0.5 Workspace 结构重构     单 crate → kernel/ + user/ + runner
P1  引导 + 双通道输出        bootloader + serial(COM1) + vga(0xB8000)
P2  中断与定时器            GDT/TSS + IDT + 8259 PIC + PIT 100Hz
P3  内存管理                位图 PMM + OffsetPageTable VMM + linked_list_allocator 堆
P4  进程与轮转调度          Task 状态机 + __switch 汇编 + RoundRobinScheduler
P5  用户态与系统调用         ring3 进入 + ELF64 装载 + int 0x80 dispatch
P6  虚拟文件系统(VFS)        trait Inode/FileSystem + 挂载表 + fd 表 + devfs/procfs/initrd
P7  设备驱动                键盘(IRQ1→/dev/kbd) + e1000 网卡(PCI/BAR/RX/TX 环)
P8  网络栈 + Shell          ethernet→arp→ip→icmp/udp/tcp→socket + 交互式 shell
收尾 文档与注释              readme 入口、操作手册入库、全工程中文注释
```

**贯穿全程的教学约束**（不是性能最优解，而是"看得懂"最优解）：

- 每个 `.rs` 文件 ≤ **400 行**、每个函数 ≤ **60 行**（超过就拆文件/拆函数）。
- 算法一律取**最朴素**实现（轮转调度、位图分配、最长前缀匹配……）。
- 用 **Rust 类型系统**表达 OS 概念：`enum` 状态机、`trait` 多态、`newtype` 包装。
- **明确不做**：SMP、COW、信号、ext2、swap——裁剪掉一切会喧宾夺主的复杂度。

## 2. 引导栈的选型与迁移（一段弯路）

这是整个项目**最早也最意外**的一次"计划赶不上变化"。原始计划写的是 `bootloader 0.9` + `cargo bootimage 0.10.5`，但实际动手时该组合在当前 nightly 上无法工作：

| 现象 | 排查 |
|---|---|
| `cargo bootimage` 无条件传 `-Zjson-target-spec` | 与现有 nightly 不兼容，直接报错 |
| `bootloader 0.9` 依赖的 `x86_64 0.14` | 在合适的 nightly 上编译失败 |
| 强行拼出的镜像启动后 | **三重故障、串口无任何输出**，无从下手 |

**决策：放弃 bootimage，迁移到 `bootloader 0.11` + cargo runner（bindeps）。** 迁移后的架构：

- **kernel 侧**：`bootloader_api::entry_point!` + 可选 `BootloaderConfig`。
- **runner 侧（根包 build.rs）**：用 `bootloader::BiosBoot` 链接 kernel 产物、生成 `bios.img`，通过 **artifact-dependency（bindeps）** 引入 `x86_64-unknown-none` 的 kernel。
- **驱动方式**：`cargo run -p simplelinux` / `Makefile` 拉起 QEMU。

迁移带来的两个必须记住的差异：

1. **0.11 用 framebuffer**（如 `0xfd000000`）而非 `0xB8000` 文本缓冲；`println!` 主要走串口。
2. **默认不映射物理内存**，需在 `config.mappings.physical_memory = Some(Mapping::Dynamic)` 显式开启——否则 Phase 3 的高半区物理访问无从谈起。

> 教训沉淀：构建入口**只能用 `cargo build/run -p simplelinux`（root runner）**；直接对 `kernel` 打包会按宿主 target 链接，触发 `duplicate symbol _start`。

## 3. 逐阶段的探索与验证

### Phase 0.5 — Workspace 结构重构（先拆再建）

计划里一个**关键修正**：原仓库是单 crate（`src/main.rs` 等），但 Phase 5 的用户态 ELF 在单 crate 下**不可行**——`bootloader` 的 `#[entry_point]` 与 user 独立 `#[no_main]` 产物冲突，无法同时产出 initrd 内的用户 ELF。因此把"拆分"前置到所有新功能之前：

- 根 `Cargo.toml` 变 workspace（`kernel` + `user`），根包同时充当 host runner。
- 现有 `main.rs/serial.rs/vga.rs` 原样移入 `kernel/src/`。
- **验证标准**：重构后 `make run` 的串口输出须与重构前**逐字节一致**（纯结构迁移、行为零变化），确认无回归后才进 Phase 2。

### Phase 1 — 引导与双通道输出

沿用 `serial.rs`（`lazy_static` + `Mutex<SerialPort>`，16550 UART @ `0x3F8`）、`vga.rs`（`Writer impl core::fmt::Write`，volatile 读写 `0xB8000`）、`main.rs` 的 `print!/println!` 双通道宏。这一阶段确立了后续所有模块复用的初始化模式：`lazy_static!` + `init()` 触发 + `_print(args)`。

### Phase 2 — 中断与定时器

- **顺序约束**：GDT/TSS 先于 IDT 加载；PIT 在调度器就绪后才启动。
- 8259 PIC 重映射 IRQ0–15 → 向量 32–47；`double_fault` 处理器绑 IST 索引（自我故障时不崩）；`breakpoint` 主动 `int3` 验证。
- PIT 通道 0，`1193182/100` 分频 → 100Hz；IRQ0 handler 递增 `TICKS` 并 `eoi`。
- **观测**：`tick=100/200/...` 每 ~1s 一行；`int3` 命中后能正常返回。

### Phase 3 — 内存管理

- `pmm.rs`：`BitmapFrameAllocator`（1 bit / 4KiB 帧），从 `boot_info.memory_map` 标记可用区。
- `vmm.rs`：`OffsetPageTable` + `Mapper`，复用 bootloader 交接的 PML4。
- `heap.rs`：`linked_list_allocator` 提供 `#[global_allocator]`，内核高地址映射 1MiB 堆。
- **铁律**：堆初始化前**不得**使用 `Vec/Box/String`；`memory::init` 必须早于一切依赖堆的模块。
- **验证**：分配 1000 帧后 `free_count` 精确 −1000、释放后复原；`vec![0u8;4096]` 可读写。

> ⚠️ 这一阶段埋着一个后来才爆的坑，详见 §4.1（位图按值迭代撑爆栈）。

### Phase 4 — 进程与轮转调度

设计核心是"**稳定槽位 + 裸指针上下文切换**"：

- `task.rs`：`Task` 存于 `Vec<Option<Task>>` 的稳定槽位（realloc 只移动结构体本身，各任务栈缓冲是独立堆内存不移动）；`KernelStack` 用 `vec![0u8; 16KiB]`。
- `context.rs`：`__switch`（`global_asm!`）**只保存/恢复 rsp + 6 个 callee-saved**（rbx,rbp,r12–r15）；`rip` 靠栈上返回地址；新任务初始帧按 `pop` 顺序写 6 个 0 + 返回地址 = `task_trampoline`，并对齐使入口 `rsp % 16 == 8`。
- `scheduler.rs`：**绝不跨 `__switch` 持有 `SCHEDULER` Mutex**（否则恢复后重入死锁）——加锁选下一个任务、算出 old/new ctx 裸指针、**释放 guard、再 `__switch`**；`schedule()` 记录并恢复进入时的 IF 状态（从 timer ISR 抢占进来时 IF 已为 0，恢复时不能再 enable）。
- timer ISR 调 `process::tick()`：唤醒到期 sleeper + 时间片递减到 0 触发 `schedule()`。
- **验证**：3 worker 逐轮交错打印；`join` 正确阻塞；32 任务两轮压力后 `heap/frames (stable)` 表示无泄漏。

### Phase 5 — 用户态与系统调用

- `gdt.rs` 扩展：加 user data(`0x1B`)/user code(`0x23`) 段 + 补全 TSS 的 `privilege_stack_table[0]`（ring3→ring0 的 RSP0）。
- `elf.rs`：手写最小 ELF64 解析（读 header/program header，避免重依赖），把 `PT_LOAD` 段映射进低地址用户区。
- `syscall/mod.rs`：`int 0x80` 裸汇编入口 → `dispatch`；**系统调用 ABI**：`rax`=号，参数 `rdi/rsi/rdx`，返回 `rax`（负值=errno）。
- 调用号：`Write=1, Exit=2, Open=3, Read=4, Close=5, Socket=6, Bind=7, Connect=8`。
- 计划里预留的退路成真：`swapgs` 兼容性存疑时退回 `int 0x80` 软件中断——最终采用 `int 0x80`，走同一 `dispatch`，更简单可靠。
- **验证**：`hello.elf`（`tools/gen_hello_elf.py` 手写汇编，`include_bytes!` 内嵌）在 ring3 打印 "hello from user" 后 `exit`。

### Phase 6 — 虚拟文件系统（VFS）

"一切皆文件"靠两个 trait 撑起：`trait FileSystem`（`root_inode`）+ `trait Inode`（`lookup/read/write/stat/list_dir`）。

- 挂载表按路径**最长前缀**匹配，路径逐级 `lookup`；全局 `FD_TABLE`（≤64），fds 0/1/2 → `/dev/console`。
- 三个具体文件系统：`devfs`（console/null/zero/kbd）、`procfs`（合成 `/proc/meminfo`、`/proc/uptime`）、`initrd`（解析 ustar 512B 头，只读）。
- initrd 传递方式：`bootloader` 无 initrd 参数 → 用 `include_bytes!` 把 `initrd.tar` 内嵌进内核，最简可靠。
- **验证**：`ls /initrd`、`cat /initrd/motd.txt`、`open("/nope")→NotFound`；ring3 侧 `open("/dev/console")+write`。

### Phase 7 — 设备驱动（键盘 + e1000）

- **键盘**：IRQ1 → 读端口 `0x60` → `pc-keyboard` 解码 → `Mutex<VecDeque<u8>>` 环形缓冲 → 注册为 `/dev/kbd`。验证靠注入 make-scancode 后从 `/dev/kbd` 读回 "hello"。
- **e1000**：PCI 配置空间扫描（`0xCF8/0xCFC`，vendor `0x8086` device `0x100E`）→ BAR0 取 MMIO → 复位 → 读 MAC → 配置 RX/TX legacy 描述符环（物理页来自 Phase 3 PMM）→ `send`/`poll_receive`。
- **验证**：启动打印 `device found / BAR0 / PCI cmd=0x107 / MAC / link up`，构造并发出一个 ARP 请求。
- ⚠️ 这一阶段的 TX 卡壳引出了整段调试史，见 §4.3。

### Phase 8 — 网络栈 + Shell

网络栈自底向上分层，每个文件严守 ≤400 行：

| 文件 | 职责 |
|---|---|
| `mod.rs` | `init`/`pump`、RFC1071 `checksum`、`next_hop_mac` 路由、分层自测 `demo` |
| `ethernet.rs` | 14B Ethernet II 头 + `MacAddr` newtype + EtherType 分发 |
| `arp.rs` | `BTreeMap<IPv4,MAC>` 学习缓存 + 请求/应答 |
| `ip.rs` | 20B IPv4 头 + 头校验和 + 按 protocol 分发 |
| `icmp.rs` | echo request/reply（支撑 `ping`） |
| `udp.rs` | 8B 头 + IPv4 伪首部校验和 + 按端口投递 socket |
| `tcp.rs` | 最小 `TcpState` 状态机（Listen→SynReceived 一步演示） |
| `socket.rs` | BSD socket 表 + `SocketInode impl Inode`（"网络也是文件"） |

- **与 VFS 的集成**：`Inode::sock_index()` trait 钩子（多态定位 socket，**无 downcast**）+ `fs::install_inode()`；`send/recv` 直接复用 socket fd 的 `write/read`。
- **Shell**：作为**内核任务**读取 `/dev/kbd`（非 ring3——用户 ELF 是手写固定产物，交互式 read-eval 在 ring3 不现实）。内置 `help/echo/ls/cat/ps/free/ifconfig/arp/netstat/ping/net/exit`；`ps`→`process::snapshot()`、`free`→PMM/heap、`ls/cat`→VFS、`ifconfig/arp/netstat/ping`→net 栈。
- **验证方式的妥协**：计划原本期望 host 侧 `ping 10.0.2.15` / `nc -u`；但受 §4.3 的 TX 限制出站不可观测，遂改为"**注入合成入站帧 → 驱动 decode/构造/应答**"的确定性内部自洽校验——各层校验和 `ok = true`、socket 经 VFS fd 成功 `read`，"网络也是文件"成立。`phase8_setup` 用 `keyboard::inject_str` 注入脚本化 shell 会话演示全部内置命令。

## 4. 关键踩坑与调优史

这些是过程中真正花时间的"硬骨头"，按影响排序。

### 4.1 no_std debug 三重故障：位图按值迭代撑爆 80KiB 栈

- **现象**：`memory::init` 阶段**静默三重故障**，串口只停在 "Boot info at"。
- **排障**：QEMU `-d int` 显示 `v=0e(#PF, err=写栈指针, CR2=RSP)` → `v=08(#DF)` → reset；用 objdump 对应 pc 定位到 `free_count`。
- **根因**：bootloader 0.11 默认 `kernel_stack_size` 仅 80KiB，而 debug 构建里 `for w in self.used`（`used` 是 `[u64;4096]` ≈32KiB 位图）会**按值把整个数组拷进栈帧**，单帧约 96KiB 直接爆栈。
- **修复**：迭代改用 `.iter()` 借用而非按值；`config.kernel_stack_size` 提到 512KiB；并把 gdt/interrupts init 放到 memory init **之前**，以便页故障能被诊断。
- **可复用经验**：no_std debug 内核里，大数组/结构体的任何**按值移动**（迭代、返回、传参）都可能撑爆小内核栈；怀疑"无输出故障"时优先 `-d int` + objdump 定位。

### 4.2 构建入口错误：`duplicate symbol _start`

- **现象**：`cargo build -p kernel` 报 `_start` 重复符号。
- **根因**：直接对 kernel 打包会按**宿主 target** 链接，与 bootloader 的入口冲突。
- **修复**：构建/运行一律走 root runner：`cargo build/run -p simplelinux`（`make build`/`make run`）。

### 4.3 e1000 TX 不完成：QEMU 10.0.13 设备模型的黑洞

- **现象**：e1000 发包后 TX 描述符环不推进——`TDH` 恒为 0、`ICR=0`、host `pcap` 抓不到任何包、看不到 ARP reply。
- **排查（guest 侧字节级全对）**：legacy 16B 描述符 layout（addr@0,len@8,tos@10,cmd@11,status@12）、identity 物理地址、bus-master（PCI cmd=0x107）、link up、`TCTL.EN=1`、`TDBAL`=ring phys、先开 TCTL 再写 TDT 门铃——全部正确。
- **判别实验**：手动 `set_ics`(写 ICS=TXQE) 后读 `ICR` 得 `0x20`，证明 MMIO 读写与 set_ics 通路完好；写 TDT 也确实执行了（`mac_reg[TDT]` 可读回），但按 master 源码 `start_xmit` 应推进 `TDH` 却没有。换 UC 私有窗口映射 BAR（排除 WB 缓存）仍不通，且引入间歇性调度卡死。
- **结论**：接受为**该 QEMU build 的已知 TX 完成限制**（emulator 级，非驱动缺陷），不无限追查。
- **对项目的影响**：Phase 8 网络验证因此从"host 侧外部可见"改为 §3 Phase 8 描述的"注入合成入站帧"内部自洽校验；Phase 7 驱动仍可用 `send()/poll_receive()` API 在包构造/环填充/帧解码层面完整演示。

### 4.4 其它小坑（工程细节）

- Rust 模块间函数调用需显式 `pub`，否则跨模块引用编译失败。
- `Option::and_then` 闭包签名要与返回值严格匹配（`Option` vs `Result` 混用易错）。
- TCP segment 构造函数的端口参数顺序（src/dst）曾传反——分层协议里凡成对参数都需反复核对。

## 5. 架构取舍（被拒绝的方案）

记录"为什么不那样做",和"为什么这样做"同样重要：

| 方案 | 拒绝原因 |
|---|---|
| 保持单 crate 扁平结构 | Phase 5 用户态 ELF 不可行（入口符号冲突） |
| 推迟 workspace 重构到 Phase 5 | 把最大结构风险压到最复杂阶段叠加，回滚代价高；前置重构使每阶段依赖清晰 |
| 换 limine / 自写 Multiboot2 引导 | 增加引导层复杂度，偏离教学重心 |
| 用 `smoltcp` 替代自写网络栈 | 省事但失去协议分层的教学价值 |
| async/await 调度器 | no_std 内核中过度复杂，轮转调度更贴合教学且可控 |
| initrd 走 bootloader 命令行传址 | bootloader 无 initrd 参数；`include_bytes!` 内嵌最简可靠 |
| 继续 bootloader 0.9 + bootimage | 见 §2，当前 nightly 不兼容、且实测三重故障无输出 |

## 6. 收尾阶段：文档与注释

功能全部落地后，做了一轮"让人读得懂"的工程收尾：

3. **全工程中文注释**：为 36 个 `.rs` 文件补充"**中英双语**"注释——每文件加中文 `//!` 模块概述 + 关键条目中文 `///` + 行内 `//`，保留原英文，纯注释改动不触碰逻辑。构建验证 0 错误、无新增告警、所有文件仍 ≤400 行。（`e1000.rs` 因已顶在 400 行硬上限且注释本就充分，本轮跳过。）
4. **开发历程文档**：即本文，沉淀路线、决策与踩坑。
